The web app (`apps/web`)

The web app (apps/web)

apps/web is the single-page app that is replacing the Next pages one screen family at a time (ADR 0015). It is a workspace package built with Vite, React and TanStack Router, styled with Tailwind and the colour tokens in styles/tokens.css (the Next pages import the same file). Client design describes where it is going.

How it reaches the browser

  • The Next pages live under /legacy. Every other root path that is not /api, /media, /locations, /sw.js, an icon or the manifest is a page of the SPA.
  • proxy.ts applies the site password to those paths, then rewrites them to /api/spa/shell, which reads apps/web/dist/index.html from disk on each request and answers no-store.
  • Hashed files are requested as /_spa/assets/…. The proxy skips them; a rewrite in next.config.js hands them to /api/spa/assets/…, which serves them as immutable and answers 404 for anything missing, never the shell.
  • The router owns /{slug}, an event’s schedule. Everything else the SPA does not own is forwarded: the catch-all route replaces the location with /legacy + path + query (a path already under /legacy is left alone), and a static route per legacy root page (app/legacy-pages.ts, checked against app/legacy/ by tests/unit/spa-legacy-pages.test.ts) keeps an event slug from shadowing /settings, /guests, and so on. While their screens are not SPA yet, ?viewSession= and ?viewMeeting= hand the /{slug} address on to the legacy schedule (forwards-to-legacy.ts).
  • Legacy pages link to the SPA with plain anchors, never Next’s Link (AppLink, which does that for every root path outside /legacy): Next has nothing to fetch there.

The files are read relative to the working directory, so the same code serves next start, and the Docker image, which copies apps/web/dist next to server.js.

Build and run

  • make build and the E2E web server run vite build apps/web before next build; the Dockerfile does the same. Next serves what is in apps/web/dist, so rebuild the SPA after changing it when testing through Next.
  • make dev runs Next on PORT + 1 and Vite on PORT (default 3000). Open the Vite port: it serves the SPA with hot reload and proxies /legacy, /api, /media and the other Next paths to Next. The shell gate does not apply in dev. A bare next dev answers root pages with the shell (503 until the SPA is built): use /legacy/... URLs with it, as the screenshots script does.
  • E2E specs call page.goto with root paths; the fixture sends them to /legacy/... so a click never lands before hydration, except an event’s own address (/{slug}, any query), which is the SPA’s schedule and is opened as it is. One spec covers the shell’s forward.

Layout and rules

apps/web/src/ follows the client layout; app/ (layout, nav bar, shell, pages), ui/ (dialog, button, tooltip, icons), schedule/, replica/, commands/ and queries/ exist so far (the replica: store, apply, feed client, sync state, a server clock offset and IndexedDB persistence keyed by event and viewer, opened as stale). dependency-cruiser enforces that the package imports packages/domain, packages/contracts and packages/api-client only (never app/, server/, utils/ or next), that nothing imports it, that features/ never imports api-client, and that it declares what it imports. See Architecture rules.

The viewer and the user picker

Who the browser acts as comes from GET /api/v1/me/identity (ViewerProvider, app/viewer.tsx): guestId is undefined until the server answers, then a guest id or null. The replica and the command runner are opened for that guest, never for one read from a persisted copy. choose and signOut call PUT/DELETE on the same path. A protected name answers guest.protected and UserMenu sends the user to the legacy login, /legacy/auth/login?guest=<id>; a successful login lands on /legacy. The picker lists the guests it is given (the event snapshot’s guests: members and hosts only, since GET /guests is closed to anonymous visitors, so a non-member cannot yet pick their name). Sign-out and a switch between names clear the device’s persisted replicas (persistence.clear()); step 13 must also close the feed and reopen the replica, the command runner and the queries for the new guestId when it changes (useScheduleSession does: the viewer is part of its effect key). The provider asks again every 5 s while the first identity fetch fails. app/keys.ts holds the newKey the runner needs.

Theme, footer and dev clock

app/theme.tsx keeps the ADR 0005 sb-theme cookie (read at start, written with the light/dark class on <html>; index.html’s inline script applies it before first paint, as the Next layout does). The footer’s version and build come from GET /api/v1/health (useHealth); its release notes are packages/domain’s. The dev clock toolbar needs devTools from the same endpoint (SB_ENABLE_DEV_TOOLS) and ?dev=1; it writes the time-override cookie and calls onChange, which the shell makes reload the app so the replica is read under the new time. The legacy toolbar’s “Send due reminders” button has no SPA counterpart.

Sync indicator, error boundary and the shell

SyncIndicator shows the replica’s link state (useSyncState: live, reconnecting after a short grace, stale) and re-renders at the instant it next changes. ErrorBoundary keeps the nav and footer when one screen crashes (try again, reload, or open /legacy). Shell (app/shell.tsx) composes theme, viewer, layout, nav, user menu, footer, boundary and dev clock from props (events, the picker’s guests, location). ShellProviders (theme and viewer) and ShellFrame are also exported, for a screen that needs the viewer before it can say what the frame shows. The schedule page mounts it.

The schedule

src/schedule/ holds the schedule screens; ScheduleScreen is the entry: a snapshot, the server’s now, links, the page’s search params (+ a setter) and slots for the sync indicator and footer. The view (view=agenda), filter chips (filter=) and narrowed rooms (loc=) live in the params; the search text and unfolded days are local. Everything is drawn from the replica: sessions, rooms and RSVPs from the snapshot, the viewer’s own 1-on-1s from snapshot.me.meetings (meetingViewsFrom; clash lines stay empty, the replica holds no other guest’s RSVPs). Times use the event’s zone, never the ambient one; the now line follows store.serverNow() (useServerNow).

The pure parts (grid-layout, column, meeting-column, agenda, fold, filters, search, meeting-rules, meeting-clash-text) are copies of utils/ with their tests: the legacy copies go with the legacy schedule at step 16. model.ts has the new pure rules (narrowing by room, matching, day folds). links.ts is the one place that decides where a session, a 1-on-1, add-session or booking link goes; today everything goes to /legacy/....

app/schedule-page.tsx composes it: useScheduleSession (replica/session.ts: openReplica, connectFeed, autosaveReplica, hidden-tab and back/forward-cache handling, plus a command runner) for the viewer from useViewer(), the events for the nav (GET /api/v1/events), the snapshot’s guests for the picker, the proposals redirect for an event not in its scheduling phase. A viewer change closes the feed and opens the event again.

Tests

Unit tests sit next to the code (*.test.ts(x)) and run in the web Vitest project under happy-dom as part of make test. Components are tested with @testing-library/react and user-event (cleanup is registered in src/test-setup.ts), through roles and names, never styling. Screens are covered by the E2E suite; there is no browser component runner.
