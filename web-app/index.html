The web app (`apps/web`)

The web app (apps/web)

apps/web is the single-page app that replaced the Next pages (ADR 0015). It is a workspace package built with Vite, React and TanStack Router, styled with Tailwind and the colour tokens in styles/tokens.css. Architecture has the whole picture.

How it reaches the browser

  • Every root path that is not /api, /media, /locations, /sw.js, an icon or the manifest is a page of the SPA.

  • server/http/web.ts applies the site password to those paths (not to /admin/**, which gets the shell: the admin API holds the gate, and the sign-in follows from it), then serves the shell: it reads apps/web/dist/index.html from disk on each request and answers no-store.

  • Hashed files are requested as /_spa/assets/…, served without the password as immutable; a missing one is a 404, never the shell.

  • The router owns / (app/home-page.tsx: the event list from GET /api/v1/events and GET /api/v1/site, or a redirect to the only event), /{slug} (an event’s address: it only forwards, replacing the entry, to /{slug}/schedule with the same search params and hash if it has params or scheduling has started, else to /{slug}/proposals; app/event-landing.tsx), /{slug}/schedule (the schedule), /{slug}/proposals/** (list, quick voting, new, edit; /{slug}/proposals/:id opens the proposal panel), the session forms, /{slug}/meetings, /guests/**, /settings (with its Account security section; /account-security redirects to /settings#security), /notifications, /auth/login, /auth/reset, /login (the site password, open to visitors without the cookie; POST /api/v1/auth/site) (app/account-pages.tsx) and /admin/** (app/admin-pages.tsx). Anything else is “Page not found”.

  • public/sw.js (registered by main.tsx outside the dev server) caches the shell and the /_spa/assets/ files. SPA navigations go to the network first and fall back to the cached shell, so a new build shows as soon as it is reachable; /api, /media and the other server paths are never touched. A page compares the shell’s build id with /api/v1/health (app/reload-offer.tsx: on load, every 5 minutes, on online and when the tab is shown). The viewer is remembered in localStorage so the saved schedule opens offline.

The files are read relative to the working directory, so the same code serves make start, and the Docker image, which copies apps/web/dist next to dist/server.

Build and run

  • make build and the E2E web server run vite build apps/web and scripts/build-server.ts (one esbuild bundle, dist/server/main.mjs; the native addons stay external); the Dockerfile does the same. The server serves what is in apps/web/dist, so rebuild the SPA after changing it when testing through the server.
  • make dev rebuilds the bundle on change, runs it on PORT + 1 with node --watch, and runs Vite on PORT (default 3000). Open the Vite port: it serves the SPA with hot reload and proxies /api, /media and the other server paths to the Node server. The shell gate does not apply in dev.

Layout and rules

apps/web/src/ holds app/ (layout, nav bar, shell, pages), ui/ (dialog, button, tooltip, icons, notices), features/schedule/, replica/, commands/ and queries/ (the replica: store, apply from packages/contracts/src/feed-apply.ts, feed client, sync state, a server clock offset and IndexedDB persistence keyed by event and viewer, opened as stale). dependency-cruiser enforces that the package imports packages/domain, packages/contracts and packages/api-client only (never server/, utils/ or db/), that nothing imports it, that features/ never imports api-client, and that it declares what it imports. See Architecture rules.

The admin pages are the SPA’s one lazy chunk (lazyRouteComponent over app/admin-pages.tsx in router.tsx). The chart wrappers (ui/charts/) import @observablehq/plot dynamically, so Plot is a third chunk, fetched when the statistics show a chart. Import admin code only from that module’s graph, and never import admin-pages statically elsewhere, or attendees download it again.

The viewer and the user picker

Who the browser acts as comes from GET /api/v1/me/identity (ViewerProvider, app/viewer.tsx): guestId is undefined until the server answers, then a guest id or null. The replica and the command runner are opened for that guest, never for one read from a persisted copy. choose and signOut call PUT/DELETE on the same path. A protected name answers guest.protected and UserMenu sends the user to the sign-in, /auth/login?guest=<id>; a successful login reloads /. The picker lists the guests it is given: the event snapshot’s guests (members and hosts) on an event page, the attendee directory (GET /attendees, everyone) on /guests. Sign-out and a switch between names clear the device’s persisted replicas (persistence.clear()); a change of guestId also closes the feed and reopens the replica, the command runner and the queries (useScheduleSession does: the viewer is part of its effect key). The provider asks again every 5 s while the first identity fetch fails. commands/keys.ts holds the newKey the runner needs.

Theme, footer and dev clock

app/theme.tsx keeps the ADR 0005 sb-theme cookie (read at start, written with the light/dark class on <html>; index.html’s inline script applies it before first paint). The footer’s version and build come from GET /api/v1/health (useHealth); for the admin, GET /api/v1/updates (useUpdateStatus) adds a red dot and the latest release; its release notes are packages/domain’s. The dev clock toolbar needs devTools from the same endpoint (SB_ENABLE_DEV_TOOLS) and ?dev=1; it writes the time-override cookie and calls onChange, which the shell makes reload the app so the replica is read under the new time.

Sync indicator, error boundary and the shell

SyncIndicator shows the replica’s link state (useSyncState: live, reconnecting after a short grace, stale) and re-renders at the instant it next changes. ErrorBoundary keeps the nav and footer when one screen crashes (try again, reload, or go to the home page). Shell (app/shell.tsx) composes theme, viewer, layout, nav, map button (MapButton, from GET /site), user menu, footer, boundary and dev clock from props (events, the picker’s guests, location). ShellProviders (theme and viewer) and ShellFrame are also exported, for a screen that needs the viewer before it can say what the frame shows. The schedule page mounts it.

The sign-in screens

src/features/sign-in/ holds LoginScreen (an emailed code link, or an email or username), ResetScreen (the reset link) and AccountSecurityScreen (protection, username, signed-in browsers). They take signInCalls(api) and, for the last, an AccountSecurityState from createAccountSecurityQuery; forms wait for the answer (useFormMutation with explainRefusals, since the server’s wording “Wrong password” is the message). app/account-pages.tsx routes them: the guest named by ?guest= comes from the attendee directory, and a login reloads the app on /.

features/sign-in/ also holds JoinScreen (/join/$token: a personal join link signs the person in and opens the event) and BootstrapScreen (/auth/bootstrap: the site-admin bootstrap link). The admin guests screen has the join-link actions (features/admin/join-links.tsx), and the event form (event-config.tsx) has the Identity select.

The schedule

src/features/schedule/ holds the schedule screens; ScheduleScreen is the entry: a snapshot, the server’s now, links, the page’s search params (+ a setter) and slots for the sync indicator and footer. The view (view=agenda), filter chips (filter=) and narrowed rooms (loc=) live in the params; the search text and unfolded days are local. Everything is drawn from the replica: sessions, rooms and RSVPs from the snapshot, the viewer’s own 1-on-1s from snapshot.me.meetings (meetingViewsFrom). Clash lines rest on other guests’ RSVPs, which the replica lacks: queries/meeting-clashes.ts fetches them from GET /meetings (debounced, after any change in store.meetingsRevision()) and withClashes merges them in. Times use the event’s zone, never the ambient one; the now line follows store.serverNow() (useServerNow).

The pure parts (grid-layout, column, meeting-column, agenda, fold, filters, search, meeting-rules, meeting-clash-text) are the schedule’s own; the legacy copies went with the Next schedule. model.ts has the new pure rules (narrowing by room, matching, day folds). links.ts is the one place that decides where a session, a 1-on-1, add-session or booking link goes: a session (/{slug}/sessions/:id) and a 1-on-1 (/{slug}/meetings/:id) open in the panel over the schedule, booking (?bookMeeting=) in a dialog, the add and edit session links open the session form in the panel (session-form, /{slug}/sessions/new with the slot or proposal as query, /{slug}/sessions/:id/edit; the former add-session and edit-session addresses land the same way). /{slug}/meetings (app/meetings-page.tsx) only redirects an old ?viewMeeting= address to the 1-on-1’s panel; outside the scheduling phase the panel is read-only.

app/schedule-page.tsx composes it: useScheduleSession (replica/session.ts: openReplica, connectFeed, autosaveReplica, hidden-tab and back/forward-cache handling, plus a command runner) for the viewer from useViewer(), the events for the nav (GET /api/v1/events), the snapshot’s guests for the picker, the schedule outside the scheduling phase (scheduleReadOnly in packages/domain: ScheduleData.readOnly hides RSVP, Edit and free slots, and a notice names the opening). A viewer change closes the feed and opens the event again.

Tests

Unit tests sit next to the code (*.test.ts(x)) and run in the web Vitest project under happy-dom as part of make test. Components are tested with @testing-library/react and user-event (cleanup is registered in src/test-setup.ts), through roles and names, never styling. Screens are covered by the E2E suite; there is no browser component runner.

Opening a panel and closing it

(anchor: MnpjIo7Y)

A session, a proposal, a 1-on-1 and a profile open in the side panel (ui/side-panel.tsx) at /{slug}/sessions/:id, /{slug}/proposals/:id, /{slug}/meetings/:id and /guests/:id. The first three are mounted by app/panel-host.tsx inside the event; a profile is mounted by app/profile-host.tsx at the root, over any page. The event’s own details are an event kind at /{slug}/details, mounted by panel-host.tsx too, over the schedule. PanelLinks opens its links, and those of any event’s session, proposal or 1-on-1. ForeignPanelHost opens the replica of an event the page behind does not belong to. app/panel-history.ts keeps the page behind it and the stack depth in history.state; SpaLinks opens these links in the panel. An address opened directly lands on the schedule (for a session or a 1-on-1), the proposals list or the directory with the panel over it (only the directory behind a profile gives it Prev and Next), and ?viewSession=, ?viewProposal= and ?viewMeeting= (also at /{slug}/meetings) redirect the same way. The proposal form is a panel kind too (proposal-form at /{slug}/proposals/new and .../:id/edit, session-form, and profile-form at /guests/edit, ADR 0021): ProposalFormHost, SessionFormHost and ProfileFormHost block history Back over unsaved changes with history.block, and leaving marks a confirmed or saved exit so the blocker lets it through. Booking a 1-on-1 stays a dialog, ?bookMeeting= on the schedule. Links from legacy pages and emails are plain anchors: build them with links.ts and utils/notifications.ts, never a second copy.

Two gotchas. The panel is role="dialog" with aria-modal="false", so dialog locators in E2E still find it while the page behind stays usable. landOnPanel replaces the entry with the list page and pushes the panel; it flushes the history after the replace, because a browser merges a replace and a push of one tick into one push, which left the landed address under the panel.

The page behind never unmounts, and what a reader did on it survives real page changes too. Search text (q), filter, sort and opened days are search params written with replace (the schedule in schedule-screen.tsx, the proposals list with filterFrom, sortFrom, withFilter and withSort in list-model.ts); the typed text stays local and its debounced value goes to q (ui/use-search-param-text.ts). Changes made while a panel is open go to the page behind (replaceBackground), and closePanel carries them over Close. Scroll is kept per history entry by ui/use-scroll-restoration.ts, keyed by useHistoryEntry (the page’s position in the stack, whatever panels are open over it). The router’s scrollRestoration is createScrollReset(), which resets the window only when the page behind changes and restores nothing itself.

Leaving over unsaved changes

useDiscardGuard (ui/use-discard-guard.tsx) is what Dialog and SidePanel use to ask “Discard your changes?” before Close, Escape or the Back arrow. It counts text, selects, checkboxes, radio groups and dates once the control was focused or pressed and now differs. Comboboxes, search boxes, number fields and file inputs are never counted; give any other control that only changes the view (a page size, a sort) a data-discard-ignore attribute. beforeUnload: true also warns when the page is left; only form panels turn it on.

Failure notices

NoticeProvider (ui/notices.tsx, mounted in ShellProviders) shows failures as role="alert" and confirmations as role="status", above any screen, so a notice outlives the control that raised it. Every Command has a describe (what it does to what, naming the session by title, day, time and room). The runner’s onFailure gives that, the problem code, and whether the retries ran out; failureMessage turns it into “Could not …” (refused, with the reason) or “might not have been saved” (gave up). A notice can carry an action; the runner sets none, as a blind re-send would use a new idempotency key.

Forms

A form waits for the server, unlike a command. useFormMutation (commands/) calls awaitMutation with an idempotency key kept only after an unreachable answer, so pressing Save again after “might not have been saved” cannot apply it twice. Any other answer, a refusal included, ends the key, because the server stores it and would refuse it with changed values. The result is one of: fields (the problem’s errors by path), a 409 (“changed by someone else”), a refusal with its reason, or unreachable. validateFields runs a zod schema per field before sending. ui/form.tsx has the controlled fields (TextField, TextAreaField, SelectField, DateTimeField, CheckboxField): label, hint and error are tied to the input, and an error is a role="alert".

Paging long lists

Every long list is paged: Pager (ui/pager.tsx), 50 rows by default with 25, 50, 100 or all, and page and pageSize in the address. usePaging (ui/use-paging.tsx) bundles the page, its handlers and the pager; search and filter reset to page 1, sort keeps the size. Counts and clashes are computed on the full set and only the result is paged. Notifications load from the server in chunks as pages are reached. The stats tables keep their page in component state, as one page holds several of them.

Not paged on purpose: the agenda (the text view of the schedule), the schedule grid, comment threads (they have “Load more”), push devices, event days and moments, the meetings column, Quick Voting and an event’s guest assignment. The agenda is the one list that stays whole: it is a time-ordered schedule with day folds, search, the “now” line and a match stepper, all of which would have to reach into the right page.
